## "30 Days" Calculation Discussion & Decision (09:43 GMT+8)

### User Question
**"还有个问题，30天？31天，28天月份怎么协调？"** (There's another question, how to coordinate 30 days, 31 days, 28-day months?)

### Problem Analysis
The user identified a potential issue with token expiry calculation:
- If we say "30 days", does it mean exactly 30 × 24 hours?
- Or does it mean "same date next month" (which could be 28, 29, 30, or 31 days)?

### Three Solutions Proposed

**Solution A: Fixed 30 Days (Recommended)** ⭐
```javascript
// Precise millisecond calculation
const THIRTY_DAYS_MS = 30 * 24 * 60 * 60 * 1000;
const expiry = Date.now() + THIRTY_DAYS_MS;
```
- ✅ Most precise: Always exactly 30 days (720 hours)
- ✅ No ambiguity: User understands "30 days" = 30 × 24 hours
- ✅ Simple implementation: Just add milliseconds
- ✅ Industry standard: JWT, OAuth2 all use fixed seconds/milliseconds
- ❌ Slightly imprecise in "calendar days" (might expire at different times of day)

**Solution B: Calendar 30 Days**
```javascript
// Same date next month (or closest)
const expiry = new Date();
expiry.setMonth(expiry.getMonth() + 1);
```
- ✅ Intuitive: "30 days" = "same date next month"
- ❌ Complex: Need to handle month-end (Jan 31 → Feb 28/29?)
- ❌ Inconsistent: Could be 28, 29, 30, or 31 days
- ❌ Not industry standard

**Solution C: Monthly**
```javascript
// Exactly 1 month later
const expiry = new Date();
expiry.setMonth(expiry.getMonth() + 1);
```
- Similar to Solution B, same problems

### Decision: Solution A (Fixed 30 Days) ✅

**User approved**: "可以，执行方案" (Okay, execute the plan)

**Rationale**:
1. **Precision** - Fixed 30 days (30 × 24 × 60 × 60 × 1000 milliseconds) is the most precise
2. **No Ambiguity** - No need to handle edge cases like Feb 28/29, month-end, etc.
3. **Industry Standard** - JWT, OAuth2, and most authentication systems use fixed time intervals
4. **Simplicity** - Easy to implement, easy to test, easy to understand
5. **User Expectations** - When users see "valid for 30 days", they expect 30 × 24 hours, not "same date next month"

**Implementation**:
```javascript
// Frontend (JavaScript)
const THIRTY_DAYS_MS = 30 * 24 * 60 * 60 * 1000;
const expiry = Date.now() + THIRTY_DAYS_MS;

// Backend (Rust)
const THIRTY_DAYS_SECS: i64 = 30 * 24 * 60 * 60;
let expiry = chrono::Utc::now().timestamp() + THIRTY_DAYS_SECS;
```

**Subscription Check Logic**:
- On EVERY `/api/desktop/verify` call, check if subscription is still active
- If expired: Downgrade to free (max_batch_size = 1), show renewal message
- refresh_token is ALWAYS 30 days (simplified logic)
- But subscription status is checked separately

## BUG FIX: Login Buttons Not Responding (10:22-10:28 GMT+8)

### Problem
- App displayed successfully but Send/Verify buttons didn't respond
- Vite dev server crashed with "SIGKILL"

### Root Cause Analysis - TWO Bugs Found

#### Bug 1: Event Listeners Outside DOMContentLoaded
**Location**: `app.js` lines 833-843

The original code structure was:
```javascript
document.addEventListener('DOMContentLoaded', async () => {
  // ... login event listeners inside here ...
  await initAuth();
});  // ← DOMContentLoaded closed here

  // ⚠️ BUG: These are OUTSIDE DOMContentLoaded!
  uploadArea.addEventListener('click', ...);
  uploadArea.addEventListener('dragover', ...);
  uploadArea.addEventListener('drop', ...);
  fileInput.addEventListener('change', ...);
  document.getElementById('process-btn').addEventListener('click', ...);
  document.getElementById('download-all-btn').addEventListener('click', ...);
```

These event listeners ran BEFORE the DOM existed (returned `null`), and may have caused conflicts.

#### Bug 2: Wrong Module Imports (Tauri v2 API)
**Location**: `app.js` lines 2-3

```javascript
import { readTextFile, writeTextFile, remove } from '@tauri-apps/api/fs';  // ❌ Doesn't exist in Tauri v2
import { appDataDir, join } from '@tauri-apps/api/path';  // ❌ Doesn't exist in Tauri v2
```

Vite error: `Module "@tauri-apps/api/fs" does not exist`

### Fixes Applied

#### Fix 1: Moved All Event Listeners Inside DOMContentLoaded
- Removed the rogue event listeners from outside `DOMContentLoaded`
- Combined all event listeners into a single `DOMContentLoaded` block
- This ensures DOM elements exist before attaching listeners

#### Fix 2: Changed Token Storage to localStorage
- Replaced `@tauri-apps/api/fs` with `localStorage` (same as settings storage)
- Token management functions now use `localStorage.setItem/getItem/removeItem`
- No longer need file system APIs

**New token storage code**:
```javascript

  }

## "30 Days" Calculation Discussion & Decision (09:43 GMT+8)

### User Question
**"还有个问题，30天？31天，28天月份怎么协调？"** (There's another question, how to coordinate 30 days, 31 days, 28-day months?)

### Problem Analysis
The user identified a potential issue with token expiry calculation:
- If we say "30 days", does it mean exactly 30 × 24 hours?
- Or does it mean "same date next month" (which could be 28, 29, 30, or 31 days)?

### Three Solutions Proposed

**Solution A: Fixed 30 Days (Recommended)** ⭐
```javascript
// Precise millisecond calculation
const THIRTY_DAYS_MS = 30 * 24 * 60 * 60 * 1000;
const expiry = Date.now() + THIRTY_DAYS_MS;
```
- ✅ Most precise: Always exactly 30 days (720 hours)
- ✅ No ambiguity: User understands "30 days" = 30 × 24 hours
- ✅ Simple implementation: Just add milliseconds
- ✅ Industry standard: JWT, OAuth2 all use fixed seconds/milliseconds
- ❌ Slightly imprecise in "calendar days" (might expire at different times of day)

**Solution B: Calendar 30 Days**
```javascript
// Same date next month (or closest)
const expiry = new Date();
expiry.setMonth(expiry.getMonth() + 1);
```
- ✅ Intuitive: "30 days" = "same date next month"
- ❌ Complex: Need to handle month-end (Jan 31 → Feb 28/29?)
- ❌ Inconsistent: Could be 28, 29, 30, or 31 days
- ❌ Not industry standard

**Solution C: Monthly**
```javascript
// Exactly 1 month later
const expiry = new Date();
expiry.setMonth(expiry.getMonth() + 1);
```
- Similar to Solution B, same problems

### Decision: Solution A (Fixed 30 Days) ✅

**User approved**: "可以，执行方案" (Okay, execute the plan)

**Rationale**:
1. **Precision** - Fixed 30 days (30 × 24 × 60 × 60 × 1000 milliseconds) is the most precise
2. **No Ambiguity** - No need to handle edge cases like Feb 28/29, month-end, etc.
3. **Industry Standard** - JWT, OAuth2, and most authentication systems use fixed time intervals
4. **Simplicity** - Easy to implement, easy to test, easy to understand
5. **User Expectations** - When users see "valid for 30 days", they expect 30 × 24 hours, not "same date next month"

**Implementation**:
```javascript
// Frontend (JavaScript)
const THIRTY_DAYS_MS = 30 * 24 * 60 * 60 * 1000;
const expiry = Date.now() + THIRTY_DAYS_MS;

// Backend (Rust)
const THIRTY_DAYS_SECS: i64 = 30 * 24 * 60 * 60;
let expiry = chrono::Utc::now().timestamp() + THIRTY_DAYS_SECS;
```

**Subscription Check Logic**:
- On EVERY `/api/desktop/verify` call, check if subscription is still active
- If expired: Downgrade to free (max_batch_size = 1), show renewal message
- refresh_token is ALWAYS 30 days (simplified logic)
